- 取り組んだレベル：基礎

- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/config.py` の検索件数設定 `RAG_TOP_K` を `5` から `10` に変更した（プロンプトやツール説明、モデルなどの他条件は変更せず固定）。

- 比較した質問と、固定した条件（モデル・対象資料など）：
  - 質問：「コンパクションとセッションをまたぐメモリの違いは何ですか？また、日々のメモは全部長期メモリになりますか？」
  - 回答モデル：`gemini-3.5-flash-lite`
  - 検索方式：ベクトル検索（`--trace` 付きで実行）
  - 対象資料：第1〜3回の講義資料（214ページ、同梱の `index.sqlite3` を使用）

- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
　- **変更前（`RAG_TOP_K = 5`）**
    - `--trace` のツール呼び出し：2回（1回目：`search_materials({'query': 'コンパクション セッション メモリ'})`、2回目：`search_materials({'query': '日々のメモ 長期メモリ 全部'})`）
    - 引用ページ・根拠：第3回・PDF p.13, 38, 39, 40, 65
    - 計測値：時間 `6.62 秒` / 入力 `6,527 tokens` / 出力 `553 tokens` / モデル応答 `3 回` / 生成API推定費用 `$0.003341 USD`
    - 回答内容：コンパクション（コンテキスト内の古い履歴の要約）とセッションをまたぐメモリ（外部保存先への記録）の違い、および毎晩の振り返り（dreaming）による選別プロセスについて正答。
  - **変更後（`RAG_TOP_K = 10`）**
    - `--trace` のツール呼び出し：1回のみ（`search_materials({'query': 'コンパクション セッション メモリ'})`）
    - 引用ページ・根拠：第3回・PDF p.13, 38, 39, 40, 65
    - 計測値：時間 `3.72 秒` / 入力 `3,828 tokens` / 出力 `537 tokens` / モデル応答 `2 回` / 生成API推定費用 `$0.002491 USD`
    - 回答内容：変更前と同じ根拠ページを引用しつつ、`memory/日付.md` と `MEMORY.md` のファイル名や「テストはpytestで行う」といった資料内の具体例まで盛り込んで回答。

- 改善した例と、残る失敗・制約：
 - **改善した例：** `RAG_TOP_K` を 5 から 10 に増やしたことで、1回目の検索結果の中に後半の質問（「日々のメモは全部長期メモリになりますか？」）の根拠である第3回 p.40 も含まれるようになり、エージェントによる2回目の再検索が不要になった。その結果、回答完了までの時間が約44%短縮（6.62秒→3.72秒）され、入力トークン数（6,527→3,828 tokens）および生成API推定費用（$0.003341→$0.002491）も削減された。
  - **残る失敗・制約：** 今回は検索対象が第1〜3回（214ページ）で関連ページが上位10件に収まったが、資料数が増えたり検索件数をさらに大きくしたりすると、無関係なページ（ノイズ）が混入して1回あたりのトークン肥大や精度低下を招く制約がある。

- 気づき・疑問：
  - **気づき：** 検索件数（`RAG_TOP_K`）を増やすと1回あたりのコンテキスト量が増えるため、当初は入力トークン数や費用が増加すると予想していた。しかし、件数不足でエージェントが複数回の検索ループ（再試行）を回すケースでは、最初から適切な件数（今回は10件）を一度に取得した方がLLMの往復回数が減り、結果として時間・トークン数・費用のすべてが効率化されることが実測できた。
  - **疑問：** 検索件数をさらに増やした場合（例：15〜20件）に、どのあたりから「再検索削減のメリット」を「ノイズ増加・コンテキスト肥大のデメリット」が上回るのか、その損益分岐点を別の質問でも検証してみたい。
